# 1: Приложение для слабовидящих: голосовое описание фото (документы и окружение)

## 1. Контекст

Слабовидящие пользователи не могут визуально прочитать документ или распознать предметы и
окружение. Фича даёт им мобильно-ориентированное веб-приложение (PWA): пользователь
фотографирует объект или документ, а система голосом зачитывает текст документа либо
описывает предметы и окружение. Карточка: `#1`.

Глоссарий (используется во всём spec):

| Термин | Значение |
|---|---|
| Обращение (Request) | Одна операция «фото → результат»: загруженное фото + выбранный режим |
| Режим (mode) | `DOCUMENT` (распознать и зачитать текст) или `SCENE` (описать окружение) |
| Результат (Result) | Распознанный текст/описание + ссылка на синтезированное аудио |
| Озвучка (audio) | Синтезированная речь (TTS), приложенная к результату |
| Слабовидящий пользователь | Единственная роль MVP (`USER`) |

Платформа и стек (зафиксировано с владельцем продукта):

- Frontend: Web PWA, Angular (камера через `getUserMedia`/выбор файла, озвучка в браузере).
- Backend: Java / Spring Boot 3 (единственный backend-стек в проекте), PostgreSQL + Flyway.
- Обработка фото: асинхронная (внешний AI-вызов медленный, p95 цикла ≤ 30 с).
- Внешний AI-провайдер (vision/OCR/TTS) — выбор вендора за architect (ADR), в spec контракт
  описан провайдер-агностично.

## 2. Гипотеза результата

Метрика успеха в карточке не задана — предлагаю и помечаю как открытый вопрос (раздел 13):

- **Целевая метрика:** ≥ 90% обращений доводится до озвученного результата (`DONE`) без
  ручного повторения; p95 полного цикла ≤ 30 с.
- **Опережающий индикатор:** доля обращений в статусе `DONE` против `FAILED`, p95 времени
  цикла (метрика `vision.cycle.p95`).
- **Когда проверяем:** пилот 2 недели на ≥ 20 слабовидящих пользователях.
- **Условие пересмотра:** доля `DONE` < 80% или p95 цикла > 45 с → пересматриваем провайдера
  и UX-сценарий.

## 4. Функциональные требования

- **FR-1-01** Авторизованный пользователь (`USER`) создаёт обращение: загружает фото (JPEG/PNG)
  и выбирает режим `DOCUMENT` или `SCENE`.
- **FR-1-02** Система обрабатывает обращение асинхронно и возвращает результат — текст и
  ссылку на озвучку.
- **FR-1-03** Для `DOCUMENT` система распознаёт текст документа (OCR) и синтезирует его
  озвучку.
- **FR-1-04** Для `SCENE` система формирует текстовое описание объектов и окружения и
  синтезирует его озвучку.
- **FR-1-05** Пользователь получает статус и результат обращения по `id`.
- **FR-1-06** Пользователь просматривает историю своих обращений с пагинацией.
- **FR-1-07** Фото обрабатывается и удаляется после завершения (DONE/FAILED); в истории
  остаются только текст, аудио и метаданные.
- **FR-1-08** Доступ к API только по JWT; пользователь видит исключительно свои обращения.

## 5. Нефункциональные требования

- Производительность:
  - `POST /requests` (приём): p95 ≤ 500 мс, p99 ≤ 1 с.
  - `GET /requests/{id}`: p95 ≤ 200 мс; `GET /requests` (список): p95 ≤ 300 мс.
  - Полный цикл (создание → `DONE`): p95 ≤ 30 с, p99 ≤ 45 с (лимитируется внешним AI).
  - Пропускная способность: 10 RPS на создание, масштабируется до 50 RPS без перепроектирования.
  - Фото: JPEG/PNG, до 8 МП, размер ≤ 4 МБ.
- Безопасность: JWT access token, одна роль `USER`; object-level доступ (чужое обращение →
  `404`); TLS 1.2+; фото шифруется at rest и не пишется в логи; аудит создания/чтения
  обращения (кто/когда); фото удаляется после обработки.
- Масштаб: ≥ 2 экземпляра backend, stateless; worker-обработка без гонок между экземплярами
  (`SELECT … FOR UPDATE SKIP LOCKED`).
- Согласованность: `requests` и `results` в одной БД; идемпотентность через `Idempotency-Key`
  (unique constraint); обработка at-least-once с дедупликацией по статусной машине.

## 7. Критерии приёмки

### AC-1-01 Создание обращения с фото и режимом
Given авторизованный пользователь (`USER`) с валидным JWT и фото в допустимом формате/размере
When отправляет `POST /requests` с `mode=DOCUMENT|SCENE` и файлом фото
Then ответ `202`, тело `{ requestId, status: "RECEIVED" }`
Проверка: stand

### AC-1-02 Запрос без токена отклоняется
Given запрос без `Authorization` или с невалидным JWT
When отправляет `POST /requests`
Then ответ `401`
Проверка: stand

### AC-1-03 Невалидный режим отклоняется
Given авторизованный пользователь
When отправляет `POST /requests` с `mode` вне `{DOCUMENT, SCENE}`
Then ответ `400` с указанием невалидного `mode`
Проверка: stand

### AC-1-04 Отсутствующий или не-изображение отклоняется
Given авторизованный пользователь
When отправляет `POST /requests` без файла или с файлом не-изображением / > 4 МБ
Then ответ `400`
Проверка: stand

### AC-1-05 Идемпотентное повторное создание
Given авторизованный пользователь уже создал обращение с `Idempotency-Key: K`
When повторно отправляет `POST /requests` с тем же `K`
Then ответ `202` с тем же `requestId`, вторая запись не создаётся
Проверка: stand

### AC-1-06 Получение своего обращения
Given авторизованный пользователь и его обращение со статусом `DONE`
When вызывает `GET /requests/{id}`
Then ответ `200`, тело `{ requestId, mode, status: "DONE", result: { text, audioUrl } }`
Проверка: stand

### AC-1-07 Чужое или несуществующее обращение скрыто
Given пользователь A и обращение пользователя B (или несуществующий `id`)
When A вызывает `GET /requests/{idB}`
Then ответ `404` (факт существования не раскрывается)
Проверка: stand

### AC-1-08 Список своих обращений
Given авторизованный пользователь с ≥ 1 обращением
When вызывает `GET /requests`
Then ответ `200` со списком только своих обращений, отсортированным по убыванию времени создания
Проверка: stand

### AC-1-09 Границы пагинации
Given список обращений
When вызывает `GET /requests?page=<невалидное>&size=<невалидное>`
Then невалидные `page`/`size` → `400`; `size` сверх максимума ограничивается; `page` за
пределами диапазона → пустой список
Проверка: stand

### AC-1-10 Распознавание текста документа и озвучка
Given обращение `mode=DOCUMENT` завершено (`DONE`)
When пользователь получает результат
Then `result.text` непустой и содержит распознанный текст документа, `result.audioUrl`
указывает на проигрываемое аудио озвучки этого текста
Проверка: stand

### AC-1-11 Описание окружения и озвучка
Given обращение `mode=SCENE` завершено (`DONE`)
When пользователь получает результат
Then `result.text` непустой и описывает объекты/окружение на фото, `result.audioUrl` указывает
на проигрываемое аудио озвучки этого описания
Проверка: stand

### AC-1-12 Недоступность провайдера → FAILED
Given внешний AI-провайдер недоступен (timeout/5xx)
When worker обрабатывает обращение
Then после 2 повторных попыток (retry с backoff) обращение переходит в `FAILED` с причиной
`PROVIDER_UNAVAILABLE`, доступной через `GET /requests/{id}`
Проверка: integration

### AC-1-13 Фото удаляется после обработки
Given обращение завершено (`DONE` или `FAILED`)
When обработка завершена
Then фото удалено из хранилища; в БД нет байтов фото — только текст/`audioUrl`/метаданные
Проверка: integration

### AC-1-14 UI: съёмка, режим, отправка и статус
Given авторизованный пользователь в приложении
When делает/выбирает фото, выбирает режим «Документ» или «Окружение» и отправляет
Then фото отправляется, отображается статус обработки обращения
Проверка: stand

### AC-1-15 UI: воспроизведение озвучки
Given обращение завершено (`DONE`) и пользователь на экране результата
When нажимает «Слушать»
Then аудио результата воспроизводится в браузере
Проверка: stand

### AC-1-16 UI: история обращений
Given авторизованный пользователь с ≥ 1 обращением
When открывает историю
Then видит список своих обращений с текстом/статусом и возможностью повторного прослушивания
Проверка: stand

## 8. SDC

| # | Слот | Решение |
|---|---|---|
| 1 | OWNERSHIP | Модуль/сервис `vision-assistant` владеет таблицей `requests` и endpoint `/requests`; consumers: Angular frontend (web). Внешний AI-провайдер — третья сторона, **нужен ADR** (архитектор выбирает вендора) |
| 2 | IDEMPOTENCY | `Idempotency-Key` + unique(`owner_id`, `idempotency_key`); повторный POST → тот же `requestId`. Worker at-least-once: переход `RECEIVED→PROCESSING` атомарен (`FOR UPDATE SKIP LOCKED`), повторная обработка детерминирована |
| 3 | CONSISTENCY | `requests` + `result` в одной транзакции (одна БД); внешний AI-вызов вне транзакции. Инвариант: `request_id` уникален, статус по конечному автомату `RECEIVED→PROCESSING→DONE|FAILED` |
| 4 | MIGRATION | `V1__create_requests.sql` (greenfield); rollback = `DROP TABLE requests` (финализирует architect); объём данных минимален |
| 5 | RESILIENCE | Внешний vision/OCR/TTS: connect timeout 2 с, read timeout 25 с; retry 2× с exponential backoff (идемпотентно); circuit breaker `visionCB` 50 %/10 с; fallback → `FAILED` с причиной, пользователю — статус, не зависание |
| 6 | BLAST RADIUS | Новые: таблица `requests`, endpoint `/requests`, DTO `RequestDto`/`ResultDto`; consumers: только Angular frontend. Breaking: нет (первая фича) |
| 7 | PROD AC | p95 цикла ≤ 30 с, error rate < 1 %, 10 RPS; метрики `vision.cycle.p95`, `request.status.failed`; kill switch `features.vision-assistant` (ConfigMap/env) |
| 8 | NOT-DOING | Без автоопределения режима (mode задаёт пользователь), без кэширования аудио/CDN, без multi-tenant, без перевода текста, без обучения модели на фото пользователя |

## 9. План проверок

- Стенд: Docker Compose (backend + PostgreSQL + эмулятор AI-провайдера), frontend Angular
  собирается локально; на живом стенде проверяются AC-1-01…AC-1-11 и AC-1-14…AC-1-16.
- Регрессия: unit-тесты backend (JUnit 5 + Mockito) и frontend (Karma/Jest); интеграционные
  тесты backend (Testcontainers: PostgreSQL, эмулятор провайдера) для AC-1-12, AC-1-13.
- Дополнительно: контрактный тест DTO `RequestDto`/`ResultDto`; нагрузочный тест создания до
  10 RPS.

## 10. Откат

Revert коммитов фичи; миграция `V1` — forward + rollback (`DROP TABLE requests`, детали в arch
doc); kill switch `features.vision-assistant` отключает фичу без деплоя.

## 11. Не делаем

- Автоопределение режима (mode выбирает пользователь) — снижает сложность и ложные срабатывания.
- Озвучка на нескольких языках — MVP только русский (язык документа — открытый вопрос).
- Кэширование и CDN для аудио.
- Обучение/дообучение моделей на пользовательских фото.
- Multi-tenancy.
- Нативный мобильный клиент (iOS/Android).
- Экспорт истории обращений.

## 13. Открытые вопросы

- Выбор вендора AI-провайдера (vision/OCR/TTS) → architect (ADR, слот OWNERSHIP).
- Топология: один backend-сервис vs модульный монолит vs микросервисы → architect (в spec
  заложен один сервис `vision-assistant`).
- Хранилище фото/аудио (S3/MinIO vs БД) → architect.
- Язык озвучки/распознавания: только русский или по языку документа → product owner.
- Метрика успеха (раздел 2) — предложена, требует подтверждения product owner.
